InvoicePro exposes a RESTful API that serves:

- Web Application
- Mobile Applications

# Design Principles

InvoicePro APIs follow these principles:

- Resource-Oriented
- RESTful
- Stateless
- Predictable

---

# REST Resource Design

APIs represent business resources rather than actions.

Examples

```http
/customers

/products

/quotations

/invoices

/payments
```

---

Correct

```http
GET /customers
```

---

Incorrect

```http
GET /getCustomers
```

---

Correct

```http
POST /invoices
```

---

Incorrect

```http
POST /createInvoice
```

---

# Base URL

Current API Base URL

```text
/api/v1
```

---

Examples

```http
GET /api/v1/customers

GET /api/v1/invoices

POST /api/v1/payments
```

---

# Resource Naming

Resources should:

- Use nouns
- Be plural
- Use lowercase
- Use kebab-case where necessary

---

Correct

```text
invoice-items

customer-contacts

organization-settings
```

---

Incorrect

```text
InvoiceItems

invoiceItems

getInvoices
```

---

# HTTP Methods

## GET

Retrieve resources.

Example

```http
GET /customers
```

---

## POST

Create new resources.

Example

```http
POST /customers
```

---

## PUT

Replace an entire resource.

Example

```http
PUT /customers/{id}
```

---

## PATCH

Partially update a resource.

Preferred for InvoicePro.

Example

```http
PATCH /customers/{id}
```

---

## DELETE

Soft delete a resource.

Example

```http
DELETE /customers/{id}
```

---

# CRUD Mapping

| Operation | HTTP Method | Example |
|------------|-------------|----------|
| List | GET | /customers |
| Get One | GET | /customers/{id} |
| Create | POST | /customers |
| Update | PATCH | /customers/{id} |
| Replace | PUT | /customers/{id} |
| Delete | DELETE | /customers/{id} |

---

# Resource Identifiers

Resources should use:

```text
UUID
```

Example

```http
GET /customers/cus_01HXABCD1234
```

---

Do not expose database auto-increment IDs.

---

# Nested Resources

Use nesting only for strong parent-child relationships.

Example

```http
GET /invoices/{invoiceId}/items
```

---

Example

```http
GET /customers/{customerId}/contacts
```

---

Avoid excessive nesting.

---

Good

```text
/customers/{id}/contacts
```

---

Avoid

```text
/organizations/{orgId}/customers/{customerId}/invoices/{invoiceId}/items
```

---

Maximum recommended nesting:

```text
2 Levels
```

---

# Bulk Operations

Bulk endpoints should be explicit.

Examples

```http
POST /customers/bulk-import

POST /customers/bulk-export

POST /invoices/bulk-send
```

---

Bulk operations should execute asynchronously when processing large datasets.

---

# Action Endpoints

Most APIs should represent resources.

Some business actions require action endpoints.

Examples

```http
POST /quotations/{id}/approve

POST /quotations/{id}/reject

POST /invoices/{id}/send

POST /invoices/{id}/duplicate

POST /payments/{id}/refund
```

---

Use action endpoints only when the operation cannot be represented through standard CRUD semantics.

---

# Search Endpoints

Prefer query parameters.

Example

```http
GET /customers?search=karim
```

---

Avoid

```http
POST /customers/search
```

unless search requires a complex request body.

---

# Filtering

Example

```http
GET /invoices?status=paid
```

---

Multiple filters

```http
GET /invoices?status=paid&customerId=cus_123
```

---

# Sorting

Example

```http
GET /customers?sort=name
```

Descending

```http
GET /customers?sort=-createdAt
```

---

# Pagination

Example

```http
GET /customers?page=1&limit=20
```

---

Future

Cursor pagination.

---

# Field Selection (Future)

Allow clients to request only required fields.

Example

```http
GET /customers?fields=id,name,email
```

---

Purpose

Reduce payload size.

---

# Resource Expansion (Future)

Support loading related resources.

Example

```http
GET /invoices/{id}?include=customer,items
```

---

Purpose

Reduce multiple API requests.

---

# File Upload Endpoints

Use dedicated endpoints.

Example

```http
POST /files
```

Response

```json
{
  "fileId": "file_123",
  "url": "..."
}
```

---

Business entities reference uploaded files instead of uploading directly within business endpoints.

---

# Long-Running Operations

Long-running operations should:

Return immediately.

Process in background.

Notify client upon completion.

Examples

- Bulk Import
- Bulk Export
- PDF Generation
- Report Generation

---

# URL Length

Keep URLs:

- Short
- Predictable
- Resource-Oriented

Avoid embedding business logic in URLs.

---

# URL Examples

Good

```http
GET /customers

GET /customers/{id}

GET /customers/{id}/contacts

POST /customers

PATCH /customers/{id}

DELETE /customers/{id}
```

---

Avoid

```http
GET /getAllCustomers

POST /createCustomer

POST /deleteCustomer

GET /fetchInvoiceList
```

---

# API Consistency Rules

Every endpoint should:

- Follow REST conventions
- Use consistent naming
- Return consistent responses
- Respect HTTP semantics
- Be versioned
- Be tenant-aware

---

# Architecture Decision

Decision

Adopt a RESTful, resource-oriented API design with predictable URI structures, standard HTTP methods, and minimal nesting.

---

Reason

A resource-oriented REST API is easy to understand, widely supported, and aligns well with InvoicePro's domain model.

---

Benefits

- Consistent API Design
- Better Developer Experience
- Easier SDK Generation
- Long-Term Maintainability
- Industry Standard

---

Trade-Off

Some business workflows require action endpoints in addition to pure CRUD.

Accepted.

---

# Chapter Summary

The API Design Style establishes the standards for designing REST endpoints in InvoicePro.

By using resource-oriented URLs, standard HTTP methods, predictable naming conventions, and consistent endpoint structures, InvoicePro delivers a clean, maintainable, and developer-friendly API that can evolve without breaking clients.

# 6. API Versioning

## Overview

API Versioning defines how changes to the InvoicePro API are introduced while maintaining compatibility with existing clients.

A well-defined versioning strategy allows the platform to evolve without disrupting integrations or requiring immediate client upgrades.

InvoicePro adopts URL-based versioning for all public and internal APIs.

---

# Versioning Goals

The versioning strategy aims to provide:

- Backward Compatibility
- Predictable API Evolution
- Safe Breaking Changes
- Long-Term Support
- Clear Upgrade Path

---

# Versioning Principles

InvoicePro follows these principles:

- Explicit Versioning
- Backward Compatibility
- Stable Releases
- Predictable Deprecation
- Minimal Breaking Changes

---

# Version Format

InvoicePro uses:

```text
/api/v1
```

---

Examples

```http
GET /api/v1/customers

GET /api/v1/invoices

POST /api/v1/payments
```

---

Future

```http
/api/v2
```

---

# Why URL Versioning?

Reasons:

- Easy to understand
- Easy to document
- Easy to test
- Supported by API gateways
- Widely adopted

---

Alternative approaches such as header-based or media-type versioning are not used.

---

# Current Version

Current production version:

```text
v1
```

---

Example

```http
https://api.invoicepro.com/api/v1/customers
```

---

# Breaking Changes

Breaking changes require a new API version.

Examples:

- Removing endpoints
- Removing fields
- Renaming fields
- Changing response structures
- Changing request formats
- Changing authentication behavior

---

Example

Old

```json
{
  "customerName": "John"
}
```

New

```json
{
  "name": "John"
}
```

Requires:

```text
v2
```

---

# Non-Breaking Changes

These changes do NOT require a new version:

- Adding optional fields
- Adding new endpoints
- Performance improvements
- Internal refactoring
- Bug fixes
- Adding optional query parameters

---

Example

Old Response

```json
{
  "id": "cus_123",
  "name": "John"
}
```

New Response

```json
{
  "id": "cus_123",
  "name": "John",
  "phone": "+91..."
}
```

Safe for:

```text
v1
```

---

# Version Lifecycle

Every API version follows:

```text
Development

↓

Beta

↓

General Availability (GA)

↓

Deprecated

↓

Sunset

↓

Retired
```

---

# Supported Versions

InvoicePro supports:

- Current Version
- Previous Major Version

Example

```text
Supported

v2

v1
```

---

Retired

```text
v0
```

---

# Deprecation Policy

Deprecated endpoints remain functional for a defined period.

Recommended:

```text
12 Months
```

---

Deprecation notices should include:

- Reason
- Replacement Endpoint
- Sunset Date
- Migration Guide

---

# Sunset Policy

After the deprecation period:

```text
Deprecated

↓

Sunset

↓

Removed
```

---

Clients should migrate before the sunset date.

---

# Backward Compatibility

InvoicePro prioritizes backward compatibility.

Breaking changes should be avoided whenever possible.

Preferred approaches:

- Add new fields
- Add new endpoints
- Introduce optional behavior

Instead of modifying existing contracts.

---

# Migration Guidelines

Each major version release should include:

- Migration Guide
- Changelog
- Upgrade Examples
- Deprecated Features
- Timeline

---

Example

```text
v1

↓

Migration Guide

↓

v2
```

---

# Version Discovery

Clients can identify the API version through:

- URL Path
- Documentation
- Release Notes

---

Future enhancement:

Response Header

```http
API-Version: v1
```

---

# Documentation

Every API version should maintain independent documentation.

Example

```text
/api/docs/v1

/api/docs/v2
```

---

Older documentation remains available until version retirement.

---

# SDK Compatibility

SDK versions should align with API versions where practical.

Example

```text
API v1

↓

SDK v1.x
```

---

# Testing Strategy

Each supported API version must have:

- Automated Tests
- Regression Tests
- Integration Tests

---

Retiring a version requires:

- Migration Validation
- Customer Notification
- Documentation Updates

---

# Security Updates

Security fixes should be backported to all supported API versions whenever feasible.

Critical vulnerabilities should be addressed immediately.

---

# Monitoring Requirements

Monitor:

- Version Usage
- Deprecated Endpoint Usage
- Upgrade Adoption
- Version Errors

---

Purpose

Guide future deprecation decisions.

---

# Future Enhancements

Future capabilities may include:

- Preview Versions
- Beta APIs
- Experimental Features
- Feature Flags
- API Compatibility Reports

---

# Architecture Decision

Decision

Adopt URL-based semantic API versioning using major versions.

---

Reason

Provides a simple, explicit, and widely supported mechanism for introducing breaking changes while maintaining compatibility for existing clients.

---

Benefits

- Predictable Evolution
- Easier Client Upgrades
- Better Documentation
- Long-Term Stability

---

Trade-Off

Multiple API versions may need to be maintained simultaneously.

Accepted.

---

# Chapter Summary

The API Versioning strategy ensures that InvoicePro can evolve without disrupting existing integrations.

By using URL-based versioning, maintaining backward compatibility, and following a structured deprecation and sunset policy, the platform provides a stable and predictable API lifecycle for all clients.

# 7. Resource-Oriented Design

## Overview

Resource-Oriented Design defines how business entities are represented and accessed through the InvoicePro REST API.

Each resource represents a real business object.

Examples include:

- Organizations
- Users
- Customers
- Products
- Quotations
- Invoices
- Payments

Resources expose standard CRUD operations wherever applicable.

Business workflows that cannot be expressed through CRUD use dedicated action endpoints.

---

# Design Principles

InvoicePro follows these principles:

- Resource First
- RESTful
- Consistent URLs
- Stateless Operations
- Predictable Endpoints
- Minimal Nesting
- Tenant Aware

---

# What Is a Resource?

A resource represents a business entity.

Examples

```text
Customer

Product

Invoice

Payment

Quotation
```

Each resource has:

- Unique Identifier
- Lifecycle
- Relationships
- Permissions

---

# Resource Collection

Collection endpoint

```http
GET /customers
```

Returns

```text
Multiple Customers
```

---

Create

```http
POST /customers
```

Creates

```text
One Customer
```

---

# Single Resource

Retrieve

```http
GET /customers/{customerId}
```

---

Update

```http
PATCH /customers/{customerId}
```

---

Delete

```http
DELETE /customers/{customerId}
```

---

# Standard CRUD Pattern

Every major resource should support:

| Operation | Endpoint |
|------------|----------|
| List | GET /resource |
| Get | GET /resource/{id} |
| Create | POST /resource |
| Update | PATCH /resource/{id} |
| Delete | DELETE /resource/{id} |

---

# Core Resources

InvoicePro exposes resources such as:

```text
organizations
```

Incorrect

Adopt a resource-oriented REST API with standardized CRUD operations, minimal nesting, and explicit action endpoints.

---

Reason

This design closely matches the InvoicePro business domain, is widely understood, and provides a predictable API for frontend applications and third-party integrations.

---

Benefits

- Consistent API Design

Trade-Off

Accepted.

- Permission
- Business Rules

---

Authorization must never rely on client-provided roles or permissions.

---

# Tenant Isolation

Every database query must include:

```text
organizationId
```

---

Cross-tenant access must be prevented at all layers.

---

Example

```text
User A

↓

Organization A

↓

Cannot Access

↓

Organization B
```

---

# Input Validation

Every request must validate:

- Required Fields
- Data Types
- Length
- Format
- Business Rules

---

Validation should occur before controller logic executes.

---

# SQL Injection Prevention

InvoicePro uses:

```text
Prisma ORM
```

---

All database access should use parameterized queries.

Raw SQL should be avoided unless absolutely necessary.

---

# Cross-Site Scripting (XSS)

User-provided data should be:

- Validated
- Sanitized where appropriate
- Safely rendered by clients

---

The API should return data as JSON only.

HTML content should not be generated by the API.

---

# Cross-Site Request Forgery (CSRF)

The primary API uses JWT bearer authentication.

Stateless bearer tokens are not vulnerable to traditional browser-based CSRF in the same way as cookie-based authentication.

If cookie-based authentication is introduced in the future, CSRF protection must also be implemented.

---

# CORS Policy

Allowed origins should be explicitly configured.

Example

```text

https://admin.invoicepro.com
```

---

Avoid

```text
*
```

for authenticated APIs.

Allowed methods

- GET
- POST
- PATCH
- PUT
- DELETE

---

Allowed headers

- Authorization
- Content-Type
- X-Request-ID
- Idempotency-Key


# File Upload Security

Uploaded files should be:

- Virus Scanned (Future)
- Size Validated
- MIME Type Validated
- Extension Validated
- Stored Outside the Application Server

---

Never execute uploaded files.

---

# Secrets Management

Secrets should never be:

- Hardcoded
- Stored in Source Control
- Logged
- Returned in API Responses

---

Examples

- JWT Secret
- Database Credentials
- API Keys
- SMTP Credentials
- Cloud Storage Secrets

---

Secrets should be managed through secure environment configuration or a dedicated secrets manager.

# API Keys (Future)

Public integrations may use API Keys.

- Rotation
- Revocation
- Expiration
- Scoped Permissions

---

API Keys should never replace user authentication for interactive clients.

# Logging Security

Security logs should capture:

- Failed Authentication
- Failed Authorization
- Permission Changes
- Rate Limit Violations
- Suspicious Requests
- Token Revocation

---

Logs must not contain:

- Passwords
- Tokens
- Secrets
- Sensitive Personal Data

# Security Monitoring

Monitor:

- Failed Logins
- 401 Responses
- 403 Responses
- Brute Force Attempts
- Suspicious IP Addresses
- Excessive API Usage

---

Critical events should trigger operational alerts.

---

# Dependency Security

Third-party dependencies should be:

- Regularly Updated
- Vulnerability Scanned
- Reviewed Before Adoption

---

Known vulnerable dependencies should be replaced promptly.

---

# Error Handling Security

Error responses must never expose:

- Stack Traces
- Database Errors
- SQL Queries
- Internal File Paths
- Infrastructure Details

---

Return generic messages to clients while logging detailed errors internally.

# Data Protection

Sensitive business data should be:

- Encrypted in Transit
- Encrypted at Rest
- Access Controlled
- Audited

---

Examples include:

- Customer Information
- Financial Records
- Organization Settings
- User Credentials

# Incident Response

Security incidents should support:

- Detection
- Containment
- Investigation
- Recovery
- Post-Incident Review

---

Critical incidents should generate immediate alerts.

# Security Testing

Regular testing should include:

- Penetration Testing
- Dependency Scanning
- Static Code Analysis
- Dynamic Security Testing
- Authentication Testing
- Authorization Testing

---

Security testing should be integrated into the release process.

# Compliance

Examples may include:

- GDPR
- SOC 2
- ISO 27001
- Local Data Protection Regulations

Compliance requirements depend on deployment region and customer obligations.

# Future Enhancements

# Architecture Decision

Implement a layered API security model combining transport security, authentication, authorization, tenant isolation, input validation, monitoring, and secure operational practices.

Reason

Benefits

- Strong Security Posture
- Better Compliance Readiness
- Improved Tenant Protection
- Reduced Attack Surface
- Enterprise Scalability

---

Trade-Off

Additional implementation complexity and operational overhead.

Accepted.

By combining secure transport, authentication, authorization, tenant isolation, validation, monitoring, and operational best practices, InvoicePro delivers a resilient and enterprise-ready API security architecture.
